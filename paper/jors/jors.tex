\section*{Abstract}

Electronic lab notebooks keep experimental notes, data and results together
as the laboratory record, but the outputs of analysis pipelines are often
copied into them by hand. labapi is a Python library that lets pipelines read
from and write to the LabArchives electronic lab notebook directly. It
presents a notebook as the same tree of folders and pages that researchers
see in the web interface, so code can address content by its notebook path
rather than by internal identifiers. labapi is archived on Zenodo, released
under the MIT licence and distributed on PyPI. It can be reused by any
laboratory whose institution provides LabArchives API access.

\section*{Introduction}

An electronic lab notebook (ELN) is most useful when it holds the whole
experimental record, including the outputs of analysis code. Once an output
is added to LabArchives, it sits beside the notes and revision history that
document the experiment \citep{labarchives}. In practice, those outputs are
often added through the web interface by hand, one page at a time, after
every pipeline run. LabArchives is a widely used commercial ELN and one of
the notebooks approved for new research in the NIH Intramural Research
Program \citep{nih_eln_policy}. It offers a web API for automating this
transfer. The API, however, addresses pages by internal identifiers rather
than by the notebook paths researchers use. Each laboratory that automates
its record-keeping must therefore write its own code to resolve paths and to
build and sign requests \citep{labarchives_api}.

labapi performs this work, so that workflows can be configured with notebook
paths. Two applications built on it are used by NIMH intramural
laboratories: muronto records neuro-behavioural experiment outputs, and
save-my-jupyter deposits Jupyter notebook snapshots
\citep{muronto,save_my_jupyter}. The intended users are computational
researchers and research software engineers who work in or with laboratories
that use LabArchives.

Benchling, RSpace and eLabFTW pair their APIs with official client libraries
\citep{benchling_sdk,rspace_client,elabapi_python}. LabArchives publishes
its API without an official client library. The public standalone
LabArchives clients listed in Table~\ref{tab:comparison} do not combine path
navigation, entry handling and attachment transfer in a single client.
Among them, labarchives-py comes closest. Its single-module implementation
signs arbitrary GET requests and returns raw responses, leaving researchers
to choose endpoints, parse responses, and implement notebook navigation,
entry handling and file transfer. Extending it would still have required
building the notebook model and higher-level record operations, so labapi
was developed as a separate client. Specialised integrations also exist for
the ReDBox research data portal and for the Model Context Protocol, but
neither provides a general-purpose, path-oriented Python interface to
notebooks \citep{redbox_labarchives,labarchives_mcp}.

\section*{Implementation and architecture}

labapi is organised in four layers. A client signs each request with
HMAC-SHA512 and handles authentication. A user session gives access to the
notebooks a researcher can open. A tree layer represents notebooks, folders
and pages, and an entry layer represents the content of a page: rich text,
headers, plain text, attachments and widgets. LabArchives returns XML, which
labapi parses with lxml.

The tree layer mirrors the hierarchy shown in the web interface
(Figure~\ref{fig:model}). Moving through this hierarchy is essential to
working with a notebook but is difficult through the raw API. The helpers
\texttt{dir()} and \texttt{page()} ensure that a folder or page exists at a
path, returning the existing node or creating it together with any missing
parent folders. \texttt{traverse()} resolves only paths that already exist.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.64\textwidth]{../figures/object-model}
    \caption{The LabArchives notebook hierarchy and the corresponding labapi
    objects.}
    \label{fig:model}
\end{figure}

The design follows the principle ``parse, don't validate''
\citep{king2019parse}. labapi parses notebook-path strings into canonical
\texttt{NotebookPath} objects, which keep track of path segments and of
whether a path is absolute or relative. All composition, resolution,
containment checks and tree traversal operate on these objects rather than
on raw strings.

\texttt{create\_json\_entry()} stores JSON as an attachment that code can
read back, and adds a formatted preview for people reviewing the page in the
web interface. A library-level meta-entry that grouped the two was
considered. It would have broken the direct correspondence between labapi
objects and native LabArchives entries, and other tools would then have
needed extra bookkeeping entries to preserve the grouping. Richer metadata
schemes were therefore left to higher-level applications.

Applications built on labapi may serve more than one researcher. API
credentials are therefore held in a \texttt{Client} object that is separate
from each \texttt{User} session, so a central application can hold several
sessions without distributing the credentials.

\section*{Quality control}

labapi is tested at two levels. A unit-test suite covers request signing and
authentication, path parsing, tree navigation, entry handling, notebook
backup and the bundled example applications. It replaces the network layer
with mocks, so it needs no credentials. A separate integration suite runs
the same operations against a live LabArchives account. It is run on demand,
because it requires institutional API credentials. GitHub Actions runs the
unit tests on every push and pull request on Python 3.10 to 3.14, together
with Ruff lint and format checks, static type checking and a documentation
build.

The repository's examples directory contains runnable workflows with sample
input data, and each example is covered by the unit tests. The JSON
synchronisation example is the quickest check that an installation works. It
uploads the two JSON files in its \texttt{sample\_data} folder to a notebook
page as JSON entries, and its download command writes them back to local
files that should match the originals.

The following workflow shows the read-and-write pattern the examples share.
A researcher adds labapi to a two-stage quality-control workflow for five
subjects from the public OpenNeuro dataset ds000228 \citep{ds000228}. In the
listings, \texttt{subjects} stands for the five subject identifiers, and
\texttt{compute\_qc()} and \texttt{summarize()} stand for the scientific
calculations. The first stage writes, for each subject, a group label and
the mean DVARS, a quality-control measure of how much a functional MRI scan
changes between successive time points \citep{power2012dvars}. It creates or
reuses one page per subject in an existing notebook:

\begin{verbatim}
user = labapi.Client().default_authenticate()
qc = user.notebooks["Lab QC"].dir("Partly Cloudy QC")

for subject in subjects:
    qc.page(f"sub-{subject}").entries.create_json_entry(compute_qc(subject))
\end{verbatim}

The second stage reads the stored values back, produces a cohort summary and
a figure, and writes both to a dashboard page:

\begin{verbatim}
notebook = user.notebooks["Lab QC"]
qc = notebook.traverse("Partly Cloudy QC")
records = [json.load(page.entries[0].content) for page in qc.children]

summary, figure_path = summarize(records)
dashboard = notebook.page("Dashboards/Cohort QC")
dashboard.entries.create_json_entry(summary)

attachment = labapi.Attachment.from_file(figure_path)
dashboard.entries.create(labapi.AttachmentEntry, attachment)
\end{verbatim}

The resulting LabArchives page is shown in Figure~\ref{fig:dashboard}.

\section*{(2) Availability}
\vspace{0.5cm}

\section*{Operating system}

Platform-independent (pure Python). Continuous integration runs on Ubuntu
24.04. labapi is also used on Windows 11 and is expected to run on macOS,
but these platforms are not covered by automated tests.

\section*{Programming language}

Python 3.10 or later; tested on Python 3.10 to 3.14.

\section*{Additional system requirements}

Network access to a LabArchives API endpoint, and an API access key ID and
password issued by LabArchives through the user's institution. The optional
browser-based login requires a local installation of Chrome, Firefox or
Edge.

\section*{Dependencies}

cryptography ($\geq$ 50), lxml ($\geq$ 6.1.1), requests ($\geq$ 2.33) and
typing-extensions. Optional extras: \texttt{builtin-auth} adds selenium and
installed-browsers for browser-based login, and \texttt{dotenv} adds
python-dotenv for loading credentials from a \texttt{.env} file.

\section*{(3) Reuse potential}

labapi can be reused by any laboratory, core facility or research software
engineer whose institution uses LabArchives and provides API credentials.
Typical uses are depositing pipeline outputs into the laboratory record,
reading earlier results back for later stages of analysis, and backing up
or exporting notebooks. The use is not tied to a scientific field: any
workflow that produces files or structured results can record them in the
notebook page that documents the experiment.

Applications can be built on labapi's object model rather than on the raw
API. Two such applications are in use at the National Institute of Mental
Health: muronto records neuro-behavioural experiment outputs, and
save-my-jupyter deposits Jupyter notebook snapshots
\citep{muronto,save_my_jupyter}. The Systems Neuroscience Imaging Resource,
an NIMH core facility that provides imaging and image-analysis support to
intramural investigators, uses labapi to back up its notebooks
automatically. Its notebook-backup support was developed with that facility
\citep{labapi_issue_264}. The repository's examples show further patterns
that can be adapted, including uploading CSV files as formatted tables and
downloading them back, synchronising a folder of JSON files with a page,
downloading a folder, and logging model runs.

Support is provided through the GitHub issue tracker, which offers forms for
bug reports and feature requests. The contributing guide describes how to
set up a development environment, run the unit and integration tests, and
submit changes through pull requests; contributors can also contact the
corresponding author. Documentation is published for each release, and each
release is distributed through PyPI and archived on Zenodo.

labapi is limited to the operations that the LabArchives API exposes, and it
cannot be used without API credentials issued by LabArchives through the
user's institution.
