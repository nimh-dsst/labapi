\section*{Abstract}

Without an API client, the outputs of analysis pipelines reach an
electronic lab notebook only when a researcher uploads them by hand. labapi
is a Python library that lets pipelines read from and write to the
LabArchives notebook directly. Code names a page by the folder path a
researcher sees in the web interface, such as QC/sub-01, and labapi finds or
creates the matching page through the API. The library is released under
the MIT licence, archived on Zenodo and installable from PyPI. It needs API
credentials, which LabArchives issues to the user's institution on request.

\section*{Keywords}

electronic lab notebook; LabArchives; research data management;
laboratory record-keeping; reproducibility; Python

\section*{Introduction}

LabArchives is a commercial electronic lab notebook (ELN) and one of the
notebooks approved for new research in the NIH Intramural Research Program
\citep{labarchives,nih_eln_policy}. An output added to a LabArchives page
sits beside the notes and revision history that document the experiment,
but getting it there from a pipeline means opening the web interface after
each run and uploading by hand. The LabArchives web API can automate the
upload. It identifies pages by internal tree IDs, however, and returns a
notebook one folder level per call \citep{labarchives_api}. Code that wants
to write to QC/sub-01 has to list the top level of the notebook, find the
QC folder by name, list that folder, find the page, and only then sign and
send the request that adds the entry. None of the public clients in
Table~\ref{tab:comparison} does this lookup, so each laboratory that
automates its record-keeping has to write it.

labapi does the lookup and the signing, and creates missing folders and
pages on request. At NIMH, two applications are built on it: muronto records
the outputs of behavioural neuroscience experiments, and save-my-jupyter deposits
Jupyter notebook snapshots \citep{muronto,save_my_jupyter}. It is aimed at
computational researchers and research software engineers in laboratories
that use LabArchives.

Benchling, RSpace and eLabFTW each ship an official Python client for their
API \citep{benchling_sdk,rspace_client,elabapi_python}, but LabArchives
publishes none. Of the standalone clients, the closest to labapi is
labarchives-py, a single module that signs arbitrary GET
requests and returns the raw responses. Choosing endpoints, parsing the XML
and walking the tree are left to the caller. Building those on top of it
would have meant writing the notebook model anyway, so labapi was started as
a separate client. There are also LabArchives integrations for the ReDBox
research data portal and for the Model Context Protocol, but neither offers
a general Python interface to notebooks
\citep{redbox_labarchives,labarchives_mcp}.

\section*{Implementation and architecture}

At the bottom of labapi, the client signs each request with HMAC-SHA512
and handles login. Above it, a user session holds the notebooks a
researcher can open, and the tree layer models their folders and pages. Page
content, whether rich text, headers, plain text, widgets or attachments
(files stored as entries), is handled by the entry layer. Responses arrive as XML and are parsed with
lxml.

Each folder and page in the tree layer corresponds to one in the web
interface (Figure~\ref{fig:model}); labapi's class names call folders
directories. A folder's contents are fetched with a
single \texttt{get\_tree\_level} call the first time code looks inside it.
\texttt{dir()} and \texttt{page()} return the folder or page at a path,
creating it and any missing parent folders if needed. \texttt{traverse()}
follows only paths that already exist.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.9\textwidth]{../figures/object-model}
    \caption{The LabArchives notebook hierarchy and the corresponding labapi
    objects.}
    \label{fig:model}
\end{figure}

Path strings are parsed once, following Alexis King's ``parse, don't
validate'' \citep{king2019parse}, into \texttt{NotebookPath} objects that
record their segments and whether they are absolute or relative. A slash
inside a name is written as \texttt{\textbackslash/}, and a malformed path
raises \texttt{PathError} when it is built, before any request is sent.
Joining, resolving, containment checks and traversal all work on these
objects.

To log in, \texttt{default\_authenticate()} opens the LabArchives sign-in
page in a browser, or prints its address, and listens on a local port for
the redirect that carries the user's one-time authentication code. The
access key ID and password are passed to the \texttt{Client} or read from
environment variables or a \texttt{.env} file.

\texttt{Notebook.backup()} saves the 7-Zip archive that LabArchives itself
produces for a whole notebook, with or without attachments.
\texttt{Notebook.export()} writes a notebook to disk as a folder tree with
one file per entry, built either by walking the API or by unpacking a
backup.

\texttt{create\_json\_entry()} stores JSON as an attachment entry that code can
read back, and adds a formatted preview for people reviewing the page in the
web interface. The two remain ordinary LabArchives entries, so other tools
that read the notebook see nothing labapi-specific. Richer metadata
schemes are left to the applications built on labapi.

API credentials are held in a \texttt{Client} object, separate from the
\texttt{User} sessions it creates. A shared service can keep one copy of
its institution's API key on the server and still open a separate session
for each researcher who signs in.

API failures are raised as typed exceptions such as \texttt{ApiError} and
\texttt{AuthenticationError}. labapi does not retry failed requests or
handle rate limiting. A folder's contents are cached once loaded, so changes
made in the web interface during a session are not seen until
\texttt{refresh()} reloads them.

\section*{Quality control}

The unit tests cover request signing and authentication, path parsing, tree
navigation, entry handling, notebook backup and the bundled examples. They
mock the network layer and need no credentials. An integration suite runs
the same operations against a live LabArchives account and is started by
hand. On every push and pull request, GitHub Actions runs the unit tests on
Python 3.10 to 3.14, along with Ruff lint and format checks, static type
checking and a documentation build.

The repository's examples directory contains runnable workflows with sample
input data. The JSON
synchronisation example is the quickest check that an installation works. It
uploads the two JSON files in its \texttt{sample\_data} folder to a notebook
page as JSON entries, and its download command writes them back to local
files that should match the originals.

A fuller example is a two-stage quality-control workflow for five subjects
from the public OpenNeuro dataset ds000228 \citep{ds000228}, in which
participants watched the short film Partly Cloudy. In the
listings, \texttt{subjects} stands for the five subject identifiers, and
\texttt{compute\_qc()} and \texttt{summarize()} stand for the scientific
calculations. The first stage writes, for each subject, a group label and
the mean DVARS, a quality-control measure of how much a functional MRI scan
changes between successive time points \citep{power2012dvars}. It creates or
reuses one page per subject in a Partly Cloudy QC folder, which holds
nothing else:

{\footnotesize
\begin{verbatim}
user = labapi.Client().default_authenticate()
qc = user.notebooks["Lab QC"].dir("Partly Cloudy QC")

for subject in subjects:
    qc.page(f"sub-{subject}").entries.create_json_entry(compute_qc(subject))
\end{verbatim}
}

Each subject page then holds the JSON attachment followed by its preview.
The second stage reads the first entry of every page back, produces a
cohort summary and a figure, and writes both to a dashboard page:

{\footnotesize
\begin{verbatim}
notebook = user.notebooks["Lab QC"]
qc = notebook.traverse("Partly Cloudy QC")
records = [json.load(page.entries[0].content) for page in qc.children]

summary, figure_path = summarize(records)
dashboard = notebook.page("Dashboards/Cohort QC")
dashboard.entries.create_json_entry(summary)

attachment = labapi.Attachment.from_file(figure_path)
dashboard.entries.create(labapi.AttachmentEntry, attachment)
\end{verbatim}
}

The resulting LabArchives page is shown in Figure~\ref{fig:dashboard}.

\section*{(2) Availability}
\vspace{0.5cm}

\section*{Operating system}

Platform-independent (pure Python). Continuous integration runs on Ubuntu
24.04. labapi is also used on Windows 11. Windows and macOS are not covered
by automated tests.

\section*{Programming language}

Python 3.10 or later; tested on Python 3.10 to 3.14.

\section*{Additional system requirements}

Network access to a LabArchives API endpoint, and an API access key ID and
password issued by LabArchives through the user's institution. The optional
browser-based login requires a local installation of Chrome, Firefox or
Edge.

\section*{Dependencies}

cryptography ($\geq$ 50), lxml ($\geq$ 6.1.1), requests ($\geq$ 2.33) and
typing-extensions ($\geq$ 4.12.2). Optional extras: \texttt{builtin-auth}
adds selenium ($\geq$ 4.39) and installed-browsers ($\geq$ 0.1.5) for
browser-based login, \texttt{dotenv} adds python-dotenv ($\geq$ 1.2.1) for
loading credentials from a \texttt{.env} file, and \texttt{export} adds
py7zr ($\geq$ 1.1.3) for unpacking notebook backups.

\section*{(3) Reuse potential}

Nothing in labapi is specific to neuroscience or to NIMH. A laboratory in
another field could use the same calls to file instrument output,
simulation results or analysis reports on the page for each experiment. A
core facility could schedule backups of the notebooks it manages, as the
Systems Neuroscience Imaging Resource, an NIMH imaging core, already does.
The backup feature was written together with that facility
\citep{labapi_issue_264}.

The repository's examples are starting points for common tasks, among them
uploading CSV files as formatted tables and downloading them again, keeping
a folder of JSON files in sync with a page, and logging model runs. To
support a LabArchives entry type that labapi does not yet
cover, a developer subclasses \texttt{Entry} with the type's name as a class
keyword, and the new class registers itself for dispatch.

Questions and bug reports go to the GitHub issue tracker, which has forms
for bug reports and feature requests. The contributing guide covers setting
up a development environment, running both test suites and opening a pull
request, and contributors can also write to the corresponding author.
Releases follow semantic versioning, as stated in the changelog. Each one is published on PyPI and
archived on Zenodo with its own documentation.
